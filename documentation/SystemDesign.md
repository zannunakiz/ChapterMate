# ChapterMate — System Design

ChapterMate is a Next.js 16 (App Router) + React 19 + TypeScript application that turns a PDF book into a voice-conversational reading companion, and its system design is best understood as one request path that is layered rather than assembled: **Clerk** owns identity at the edge (`proxy.ts` runs `clerkMiddleware`, marking `/`, `/books`, `/books/session/*` and `/home` public while `auth.protect()` guards everything else), every server action re-resolves `userId` with `auth()` instead of trusting the browser, and **MongoDB Atlas** (through a cached Mongoose 9 connection in `database/mongoose.ts`, with a `lib/dns-bootstrap.ts` SRV fallback for restrictive networks) stores three collections — `books`, `booksegments` and `voicesessions`. The **Vercel Blob** store holds the binary assets the database only references (`fileURL`/`fileBlobKey` for the PDF, `coverURL`/`coverBlobKey` for the cover), **pdfjs-dist** extracts the text and renders page 1 as the cover *inside the browser* so no heavy parsing runs on the server, and **Vapi** (`@vapi-ai/web` with ElevenLabs `11labs` voices) turns those parsed segments into a live spoken conversation whose retrieval requests come back to the app through `/api/vapi/search-book` — i.e. identity leads, the database and blob store hold state, PDF parsing happens closest to the file, and Vapi is the only component that reaches *back* into this stack rather than being called by it.

The flow therefore reads as a relay between the two halves of the stack that never talk directly: the upload half runs `checkBookExist → parsePDFFile → /api/upload → createBook → saveBookSegments`, fanning a single PDF into a `Book` document plus hundreds of ranked `BookSegment` documents, while the session half runs `startVoiceSession → vapi.start({ variableValues: { bookId } }) → searchBook tool → searchBookSegments(bookId, query, userId)`, so a spoken question becomes a MongoDB `$text` query (with a keyword-regex fallback) whose top segments are returned as the assistant's grounded answer, and `endVoiceSession` closes the accounting loop by writing `endedAt`/`durationSeconds`. Around that core, engineering quality is enforced uniformly: **Zod + react-hook-form** validate uploads and upload constants cap size/type at both client and server, **feature flags** (`FF_DUMMY_BOOKS`, `FF_DUMMY_FORM`) allow the same UI to run on bundled sample data or live data, **PostHog** is initialised exactly once in `instrumentation-client.ts` with slug-masked `$pageview` events from `components/posthog-page-view.tsx` (and Vercel Analytics alongside it) so private book titles never leave the app, and the same invariants are pinned by **Jest** unit tests in `__tests__/` that mock Clerk, Mongoose and Vercel Blob to assert ownership, the 10-book limit, the access filter and the search behaviour — all of which **GitHub Actions** (`.github/workflows/unit-tests.yml`) runs on every push and pull request as three independent jobs: `unit-tests`, `lint` and a production `build`.
